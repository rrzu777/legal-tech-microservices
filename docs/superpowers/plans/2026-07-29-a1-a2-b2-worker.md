## Evidencia

Los tres bugs, medidos contra producción el 29 jul 2026.

**A2-a — `C-1000-2024`**, `sync_attempts=11`, nunca sincronizó:

```
invalid input syntax for type date: "Firmado"   (Postgres 22007)
```

`normalize_date` (`app/parsers/normalizer.py:80`) termina en `return raw`: si el string no
es ISO ni `DD/MM/YYYY`, **devuelve el texto crudo** y el worker se lo manda a una columna
`date`. `"Firmado"` es un valor de la columna *estado*, o sea que además el mapa de columnas
está corrido para esa tabla — pero eso no se puede arreglar a ciegas y el normalizador
fail-safe cubre cualquier corrimiento futuro.

**A2-b — `T-100-2024`**, `sync_attempts=11`, último sync el 2026-03-13:

```
ON CONFLICT DO UPDATE command cannot affect row a second time   (Postgres 21000)
```

`_upsert_movements` (`worker/engine.py:589`) manda el batch entero sin deduplicar. La clave
es `case_number:cuaderno:folio` (`engine.py:93`) y un mismo folio puede tener más de un
trámite → dos filas con la misma clave en el mismo `upsert` → Postgres lo rechaza entero.

**A1 — el pool**: ~12% de fallo de minteo, uniforme, desde el día 1. `_mint_slot`
(`worker/session_pool.py:96`) llama `minter.mint()` una sola vez y si falla, el slot se
queda con la sesión vieja y la causa cuenta un fallo.

**B2 — el heartbeat miente**. Fila real:

```json
{"cases_synced_today": 12, "errors_today": 1, "pool_size": 1, "metadata": {}}
```

`pool_size: 1` con **3 slots corriendo**: `session_pool.py:47-48` usa
`OJV_PROXY_POOL_SIZE` (3) cuando hay proxy, pero `metrics.py:50` reporta `config.POOL_SIZE`
(1). Y `errors_today` mezcla fallos de infra con fallos de causa, que son cosas distintas.
`metadata` es un jsonb vacío listo para usar — **sin migración**.

```python
def normalize_date(raw: str | None) -> str | None:
    """Normaliza a ISO (YYYY-MM-DD). Devuelve None si no es una fecha.

    Devolver el string crudo cuando no parsea era una bomba de tiempo: el worker
    manda esto a una columna `date` de Postgres, asi que cualquier corrimiento del
    mapa de columnas del parser terminaba en `invalid input syntax for type date`
    y, a los 10 intentos, en una causa suspendida (paso con C-1000-2024, que
    recibio "Firmado" — un valor de la columna estado).
    """
    if not raw:
        return None
    raw = raw.strip()
    if not raw:
        return None
    if _DATE_ISO_RE.match(raw):
        try:
            date.fromisoformat(raw)
        except ValueError:
            logger.warning("Fecha ISO invalida, se descarta: %r", raw)
            return None
        return raw
    m = _DATE_DMY_RE.match(raw)
    if m:
        d, mo, y = int(m.group(1)), int(m.group(2)), int(m.group(3))
        try:
            return date(y, mo, d).isoformat()
        except ValueError:
            logger.warning("Fecha DMY invalida, se descarta: %r", raw)
            return None
    logger.warning("Valor no reconocido como fecha, se descarta: %r", raw)
    return None
```

Aflojar `_DATE_DMY_RE` para aceptar uno o dos dígitos:

```python
_DATE_DMY_RE = re.compile(r"^(\d{1,2})/(\d{1,2})/(\d{4})$")
```

Y arriba del archivo: `import logging`, `from datetime import date`, `logger = logging.getLogger(__name__)`.

## Task 2: A2-b — claves duplicadas dentro del mismo upsert

Decisión de diseño: **no se descarta el movimiento duplicado**. Deduplicar quedándose con
el último perdería un movimiento de una causa judicial en silencio, que es exactamente lo
que este proyecto existe para evitar. Y cambiar la clave para todos rompería la
correspondencia con las filas ya guardadas → todo se reinsertaría como "movimiento nuevo" y
se dispararían notificaciones falsas en todas las causas.

La salida: la **primera** ocurrencia conserva la clave de siempre (compatibilidad hacia
atrás intacta) y las siguientes reciben un sufijo `#2`, `#3`. Nada se pierde, nada se
reinserta.

En `worker/engine.py`, junto a `_build_external_movement_key`:

```python
def _dedupe_movement_keys(keys: list[str]) -> list[str]:
    """Desambigua claves repetidas dentro de un mismo batch de upsert.

    La clave es `case_number:cuaderno:folio` y un mismo folio puede tener mas de un
    tramite, asi que dos filas del mismo batch pueden colisionar. Postgres rechaza
    el upsert ENTERO con 21000, no solo la fila repetida.

    La PRIMERA ocurrencia conserva la clave de siempre — las filas ya guardadas
    siguen matcheando y no se reinsertan como movimientos nuevos — y las que siguen
    llevan sufijo. No se descarta ninguna: perder un movimiento de una causa en
    silencio es peor que el bug original.
    """
    seen: dict[str, int] = {}
    out: list[str] = []
    for key in keys:
        n = seen.get(key, 0) + 1
        seen[key] = n
        out.append(key if n == 1 else f"{key}#{n}")
    return out
```

En `_upsert_movements`, después de construir `rows` y antes del upsert:

```python
        keys = _dedupe_movement_keys([r["external_movement_key"] for r in rows])
        n_dupes = sum(1 for k in keys if "#" in k)

                "Causa %s: %d movimiento(s) con cuaderno+folio repetido en el mismo "

                case["case_number"], n_dupes,
```

## Task 3: A1 — retry con backoff en el minteo

Con fallos independientes al ~12%: **12% → ~1,5% con un reintento, ~0,2% con dos.**

Dos cuidados de diseño:

1. Cada reintento tiene que pedir un **token nuevo** (o sea, una IP nueva). Reintentar
   contra la misma IP sticky que acaba de fallar no arregla nada.
2. El retry va **dentro** del intento de minteo, después del cooldown `BLOCK_PAUSE_S` que
   está al principio de `_mint_slot`. Ese cooldown existe para que un slot que re-mintea en
   loop no queme IPs; los reintentos internos no lo re-disparan.
